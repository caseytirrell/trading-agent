# Claude Trading Agent Project Handoff

## Project purpose

`claude-trading-agent` is a Next.js TypeScript application for controlled Alpaca paper trading. Despite the repository name, the current AI provider is OpenAI because the project owner has OpenAI API credits.

The app is intentionally paper-trading only. The AI is used as an analyst that can recommend a trade, but application code is the risk manager and final execution gate. Alpaca executes only paper orders that pass local validation.

## Current stack

- Next.js `16.3.8`
- React `19.2.4`
- TypeScript with `strict` enabled
- App Router under `src/app`
- Tailwind CSS v4
- Official `openai` npm package
- Direct Alpaca REST calls with built-in `fetch`

The Alpaca JavaScript SDK is not used.

## Environment variables

Server-side variables are expected in `.env.local`:

```bash
ALPACA_ENDPOINT=https://paper-api.alpaca.markets
ALPACA_API_KEY=your_paper_key
ALPACA_SECRET_KEY=your_paper_secret
OPENAI_API_KEY=your_openai_api_key
TRADING_ENABLED=false
DATABASE_URL=your_pooled_neon_connection_string
DIRECT_URL=your_direct_neon_connection_string
```

Important rules:

- Do not use `NEXT_PUBLIC_` for secrets — this includes both database URLs.
- Do not expose Alpaca, OpenAI, or database secrets to client components.
- Keep `.env.local` ignored by Git (`.env.local.example` holds placeholders).
- Do not add live trading support without an explicit project decision.

`TRADING_ENABLED` is fail-closed: trading is allowed only when its exact value
is `true`. Missing, malformed, or `false` values activate the server-side kill
switch.

Production env vars are not configured yet; the database is wired up for
local development only.

## Database persistence (Phase 2)

- Provider: Neon Postgres (project/database `trading-agent-paper`, branch
  `production`, region `us-east-1.aws`, Postgres 18, `pgcrypto` enabled,
  free plan).
- `DATABASE_URL` is the pooled Neon connection string used at runtime;
  `DIRECT_URL` is the direct connection string used only by Prisma tooling
  (`directUrl` in the datasource).
- **The schema is managed manually.** All 13 tables were created by hand in
  the Neon SQL Editor. `prisma/schema.prisma` maps those snake_case tables
  exactly (verified with `prisma migrate diff`, which reports no difference).
  There are intentionally **no migration files and no baseline**: Prisma
  never owns this schema. Never run `prisma migrate dev` or `prisma db push`.
- Typed access is via Prisma Client 6 (`@prisma/client`), generated by
  `prisma generate` (wired as the `postinstall` script).
- `src/lib/db.ts` is the server-only Prisma singleton (`import "server-only"`
  makes any client-component import a build error).
- `src/lib/db-serialization.ts` holds pure JSON/date/decimal mapping helpers
  (unit-tested; no Prisma or env access).
- `src/lib/persistence.ts` holds all write/read helpers. Every helper is
  **best-effort**: a database outage logs the error and returns null — it
  never throws into a trading or analysis flow and never changes what the
  app does. Persistence is observability, not control flow.

Persistence coverage:

- `POST /api/agent/run`: creates an `agent_runs` row (`running` →
  `completed`/`failed`, or a single `skipped` row when the kill switch or
  paper-endpoint guard refuses the run), saves the deterministic market
  analysis, the AI recommendation, the risk decision (with account /
  positions / recent-orders / market-clock snapshots), an
  `alpaca_order_refs` row when an order is submitted, and `error_events` on
  failure. The response now includes a non-breaking `agentRunId`.
- `POST /api/openai/recommendation`: recommendation only,
  never places orders; records the run, analysis, recommendation, and a
  `recommendation_preview` risk decision.
- `POST /api/agent/evening-analysis`: unchanged analysis-only contract
  (`analysisOnly: true`, `ordersSubmitted: 0`, `ordersQueued: 0`, no order
  imports); records the run, the market analysis, and the report with its
  candidates (`evening_analysis_reports` + `evening_analysis_candidates`).
  The response now includes non-breaking `agentRunId` and `reportId`.
- Helpers exist (but nothing calls them yet) for `scheduled_job_runs`,
  `notifications`, `app_settings` + `settings_audit_logs` (audited upsert in
  one transaction), and age-based retention cleanup (`prune*` functions —
  deliberately not scheduled in this phase).

Safety boundaries preserved:

- Alpaca remains the broker source of truth. `alpaca_order_refs` rows are
  local references only and must be reconciled against Alpaca before being
  treated as fills.
- Nothing reads database rows back as trade instructions. The risk manager
  (`runRiskCheck`) remains the only execution gate, the kill switch and
  paper-endpoint enforcement are untouched, and the AI still cannot submit
  orders.

## Evening Analysis history (Phase 3)

Saved Evening Analysis reports are now first-class read-only history. No
database schema change was needed — the manually managed tables already had
every required column, and data freshness is read from the persisted
`market_analyses.summary`/`candidates` JSON (`asOf`, `forceNoTrade`,
`dataIssues`, per-symbol `lastBarDate`).

Expiration rule (server-side, conservative — no holiday/early-close
calendar yet):

- A report is valid only for its `intended_session_date` (the Eastern
  calendar date of the next session at generation time).
- If `intended_session_date` is before today in **America/New_York**, the
  report is expired.
- If `expires_at` is set and now >= `expires_at`, the report is expired.
- If `intended_session_date` is null, the report is never expired by the
  sweep but is permanently **not eligible for revalidation**.
- A status other than `active`, an `expired_at` marker, or any unparseable
  stored value all fail closed to expired.
- `expireOutdatedEveningAnalysisReports` applies the rule by setting
  `status = "expired"` and `expired_at = now()`. It runs opportunistically
  from the read helpers — there is **no background scheduling** — and it
  never deletes rows (retention pruning stays separate and manual).

Read-only report endpoints (no OpenAI, no Alpaca, no order path, no
secrets):

- `GET /api/agent/evening-analysis/reports` — latest 20 report summaries
  (newest `generated_at` first; `?limit=` clamped to [1, 50]) with
  server-computed validity: `validity` (`active`/`expired`), `isExpired`,
  `eligibleForRevalidation`, `validityReasons`.
- `GET /api/agent/evening-analysis/reports/[id]` — one full report with its
  candidates (WATCH/MONITOR/NO_TRADE labels preserved), entry levels as
  recorded, per-symbol `lastBarDate` freshness, and the same validity
  fields. The browser-supplied id is validated server-side (UUID check
  before any lookup). Expired reports are returned for history viewing but
  are always explicitly flagged.

How persisted history must be interpreted:

- Saved reports are **historical analysis, not trade authority**. Prices,
  scores, and eligibility were valid only at generation time. Alpaca remains
  the broker source of truth.
- Expired reports are history only. They can never be used by future
  execution or revalidation flows. Candidate DTOs carry `executable: false`
  and `reportExpired` so a detached candidate stays self-describing.
- Validity is computed by the server (`computeEveningReportValidity` in
  `src/lib/evening-report-history.ts`, unit-tested including the
  America/New_York date handling). The client only displays it.
- `getLatestValidEveningAnalysisReport` exists as **Phase 4 preparation
  only** — nothing calls it yet. It fails closed to null whenever the
  database is unavailable or validity cannot be affirmatively determined,
  and it refuses expired / never-revalidatable reports. Even a report it
  returns must be revalidated against live data and pass the deterministic
  risk manager before any future execution phase acts.
- Still absent by design in Phase 3: scheduling, morning revalidation,
  next-day execution, any order submission from Evening Analysis, and any
  automatic order queue.

Dashboard: `EveningAnalysisCard` now embeds
`src/components/EveningAnalysisHistory.tsx`, a read-only history browser
(manual "Load saved reports" button — no polling, no timers). It labels
each report Active / Active — not revalidatable / Expired — history only,
preserves WATCH/MONITOR/NO_TRADE badges, and shows data freshness
(analysis `asOf`, per-candidate "data through" bar dates). The
"Run Evening Analysis" button remains manual and unchanged.

## Alpaca order behavior

Orders are submitted by `placePaperMarketOrder` in `src/lib/alpaca.ts`.

The current order body is:

```ts
{
  symbol,
  qty,
  side,
  type: "market",
  time_in_force: "day",
  client_order_id: clientOrderId,
}
```

This is a regular-session day market order. The app does not set
`extended_hours: true`, and the risk manager blocks submissions while the
Alpaca market clock is closed. A filled price is only available after Alpaca
reports an execution.

`placePaperMarketOrder` refuses to submit unless `ALPACA_ENDPOINT` includes `paper-api`.

Every order-capable route shares one process-wide execution lease. A second
request received while another request is evaluating or submitting returns
HTTP 409. Each broker submission also uses a deterministic `client_order_id`
for the symbol, side, quantity, and Eastern trading date. If a retry reaches
Alpaca after the original request succeeded, the app retrieves and returns the
existing order instead of creating a duplicate.

The execution lease is process-local. Broker-side `client_order_id`
deduplication protects the same trade intent across multiple server instances,
but coordinating different simultaneous trade intents across multiple
instances would require a shared lock if the app is deployed horizontally.

Recent order retrieval now uses:

```text
/v2/orders?status=all&limit=50&direction=desc
```

This makes the dashboard less likely to miss recent activity and shows the newest orders first.

## OpenAI recommendation behavior

OpenAI is called by `getOpenAITradeRecommendation`.

It receives:

- Account summary
- Current positions
- Latest trades for approved symbols
- Optional market clock

It must return structured JSON:

```ts
{
  action: "BUY" | "SELL" | "HOLD" | "NO_TRADE";
  symbol: ApprovedSymbol;
  qty: number;
  confidence: number;
  reason: string;
}
```

The returned JSON is parsed and validated before reaching the risk manager.

The manual recommendation card never executes a trade. It only displays the recommendation and whether the risk manager would consider it executable.

## Approved trading universe

The approved symbols are defined only in `src/lib/trading-universe.ts`:

```ts
SPY, QQQ, AAPL, MSFT, NVDA, AMZN, GOOGL, META, TSLA, AVGO, AMD, COST, JPM, V, UNH
```

Symbol validation should always import from this file. Do not define duplicate symbol lists.

## Risk manager rules

`runRiskCheck` in `src/lib/risk-manager.ts` is the final local execution gate.

Current rules include:

- Trading must not be disabled by `TRADING_ENABLED=false`.
- Alpaca endpoint must be paper only.
- Symbol must be in `APPROVED_SYMBOLS`.
- Quantity must be a whole number.
- Maximum quantity is 1 share.
- Side must be `buy` or `sell`.
- Market must be open.
- AI trades require confidence of at least 0.7.
- Maximum 3 trades per Eastern calendar day.
- No duplicate open order for the same symbol.
- Do not buy a symbol already held.
- Do not sell more than the held quantity.
- Buys require positive cash.
- Stop trading after a daily loss of at least 2% of portfolio value.

The risk manager returns:

```ts
{
  approved: boolean;
  reasons: string[];
}
```

## Autonomous agent behavior

`POST /api/agent/run` performs one controlled run:

1. Confirm the Alpaca endpoint is paper.
2. Check the kill switch.
3. Fetch account, positions, recent orders, approved-symbol latest trades, and market clock.
4. Ask OpenAI for one recommendation.
5. If OpenAI says `HOLD` or `NO_TRADE`, do not submit an order.
6. Convert `BUY` or `SELL` into a concrete trade request.
7. Run the risk manager.
8. Place a paper market order only if approved.
9. Return recommendation, risk result, order result, skipped reason, and timestamp.

Client-side Auto Mode is in `AutonomousAgentCard`.

- Default interval is 30 minutes.
- Minimum interval is 15 minutes.
- It runs only while the dashboard is open.
- It prevents overlapping runs.
- It stops when the kill switch is active.

## Known limitations and next safe improvements

- There are no automated tests yet for the risk manager.
- Daily trade counting currently depends on the fetched recent orders. With `limit=50`, this is better than before, but a date-filtered Alpaca order query would be more robust.
- Buy-side cash validation only checks positive cash; it does not estimate whether cash covers the current price of the requested share.
- The dashboard refresh is manual. A light polling option every 30-60 seconds could be added later if desired.
- The read-only account/orders routes do not block live endpoints. Order placement is protected, but live account display should also be guarded before this project is ever connected to non-paper credentials.
- Persistence is best-effort by design: if the database is down, runs still work and the persisted ids in API responses are null. Rows can therefore have gaps; treat them as history, not as a ledger.
- The AI recommendation's raw provider response is not captured yet (`ai_recommendations.raw_response` stays `{}`); only the validated payload is stored.
- The manual order routes (`/api/alpaca/orders/place`, `/api/alpaca/orders/test-buy`) do not write `alpaca_order_refs` yet — only the agent run route does.
- Retention (`prune*` helpers) and the scheduled-job/notification/app-settings helpers exist but nothing invokes them yet; that is future-phase work.
- `npm audit --omit=dev` currently reports 4 affected dependency entries
  (3 high, 1 moderate), while the full dependency-tree audit reports 9
  (6 high, 3 moderate); neither reports a critical finding. The remaining
  advisories are transitive through Prisma/configuration, test/lint tooling,
  and browser-compatibility data. Automatic audit fixes would change versions
  beyond the approved Next.js security patch, so they were not applied.
